Actual release → proposed user experience

A coherent way to configure, install and use a capability.

This is a UX walkthrough of the released AACT, followed by concrete screen proposals. The main failure is that one task—configure this MCP—branches into different editors, hidden prerequisites and unexplained state. The user cannot reliably predict what Enter will do or where to recover.

I built this tool and previously overstated its match to the approved design. These captures show the remaining gaps directly.

Released v0.1.4test-wsl · WSLExisting tmux · keyboard walkthrough17 short journeysUX proposals · no implementation plan

The immediate dead end

The top Configure command requires a target selection but does not offer it. The lower MCP command opens a second route with multiple editors. Some failures appear only in status text; others open a clipped JSON-heavy dialog with no direct correction route. Those behaviours compound: there is no clear next step, no consistent form, and no reliable recovery screen.

The user’s complaint is supported by the walkthrough. The blue two-panel appearance does not establish a usable interaction model. A command must reveal its next step, an input must be editable at its location, and a failed operation must explain what happened in the foreground.
Keep the approved layersL1 overview → L2 related details/actions → an inset L3/L4 workspace. A simple L3 stays a centred dialog.
One configuration workspaceSetup, authentication and parameter editing share fields and keyboard behaviour. Shortcuts select a section.
Show achieved stateSaved values, installed skills, running server, reachable endpoint and agent registration are separate facts.

Current images reproduce the actual tmux cells and ANSI colours. Proposed blue screens are new static UX illustrations, not screenshots of working software. Expandable evidence below each journey links to additional observations. Click any image to inspect it at full size.

The navigation contract

The layer model below comes from the user’s instructions. The proposed wording, entry labels and recovery screens in this report remain proposals for review.

Outside text editing

  • Up / Down select within the focused pane only. Page keys scroll that pane.
  • Enter on L1 focuses L2. Enter on an actionable L2 row opens its L3 detail.
  • Left / Right and Tab move pane focus. The L3 selection determines L4 content.
  • L4 selection and scrolling never move L3. Tab also reaches the visible Save / Cancel buttons.
  • Escape returns one visible layer or focus level. Main menu remains visibly accessible with m / F9.

Inside a field

  • Enter begins in-place editing of the existing value.
  • Typing and terminal paste enter text there. Left / Right move the cursor.
  • Backspace deletes text while editing; on a collection row it removes the selected item.
  • Enter finishes the field edit. Escape abandons only that current edit.
  • Ctrl-S commits the active edit, validates and invokes the one Save-and-apply action. Errors keep the draft visible.

Scroll is visible: each scrollable pane has an indicator at the edge and ↑ / ↓ More content when appropriate. A position count is supplementary. The action bar remains reachable and visible at smaller sizes.

All editable forms use the same shape: sections on L3, only the selected section on L4. Fixed target inputs stay out of edit controls; Information records their values and origins. Read-only facts look different from menu entries. No batch selection.

01 · A working way into configuration

An apparently available command must take you to its next step. A hidden prerequisite cannot turn Enter into a dead end.

Current · observed in the release
Walkthrough
  1. Highlight Cluster Inspector on the left.
  2. Enter moves to its right panel. Highlight Configure / install.
  3. Press Enter.

What actually happens

  • The screen stays put. The only explanation is in the bottom status area: “Multiple environment targets are available; select the target in Environments.”
  • The row offers no hint that a target must first be selected. It supplies neither a target chooser nor a link to one. The user has to discover a different management screen.
  • The right panel lists a generic profile name, cluster-inspector, instead of the sample-env / target-a identity needed to distinguish configurations.
Proposed · not implemented
The same journey should be
  1. L1 Cluster Inspector → Enter: focus L2.
  2. L2 Set up another target → Enter: choose sample-env / target-a here.
  3. Enter the chosen target: open its configuration workspace.

How this should behave

  • Use two explicit entry types: “Set up another target…” and a row for each existing configured target, labelled with environment / target.
  • Set up opens a centred target chooser at L3. Show only applicable target presets, plus “Without an environment preset”. Selecting a target replaces the chooser with the L3/L4 editor. It does not add a fifth layer.
  • Opening an existing target goes straight to that target’s workspace. If a prerequisite is missing, show it in that workspace with the action needed to resolve it.

02 · Package, target, server, registration

“Configure / install” and “MCP” represent different objects without telling the user what either one owns.

Current · observed in the release
Walkthrough
  1. Select the MCP · cluster-inspector row in L2.
  2. Enter opens its Actions menu.
  3. Inspect Authenticate, Edit parameters, registrations, and runtime actions.

What actually happens

  • The menu splits one configuration task across Authenticate and Edit parameters. Both can request overlapping inputs, through different editors.
  • Start is available for a never-started profile while Configure registrations is disabled because there is no endpoint. The menu gives reasons, but no visible route connecting the steps.
  • View details reports source and target, then “Runtime: never-started · owner: local”. It supplies very little of the information needed to decide what to do.
Proposed · not implemented
The same journey should be
  1. L2 sample-env / target-a → Enter: open that target.
  2. L3 Overview → Right: read server and registration state.
  3. Choose Authentication or Connection on L3 to change configuration without hunting another menu.

How this should behave

  • A capability is the installable package. A target is one saved configuration of that package. A server is the observed MCP runtime. A registration is an agent’s connection to it. Put those distinctions in the UI through labels and concrete state.
  • The existing target opens one paired workspace: Overview, Connection, Authentication, Databases, Agents, Logs, Information. Authenticate becomes a shortcut to Authentication in this same workspace.
  • Overview explains the next usable action and shows Start / Stop only with their actual ownership constraints. Configuration remains possible before a server has ever run.

03 · One task, one editor

The editor’s shape and behaviour currently depend on the route used to reach it.

Current · observed in the release
Walkthrough
  1. Open Authenticate from the profile menu.
  2. Compare it with Edit parameters for the same target.
  3. Open setup via Environments and compare again.

What actually happens

  • Authenticate uses a full-screen “Edit package inputs” list of 14 inputs. Edit parameters opens the paired section editor, titled “Install”.
  • The Environments route can replace the whole screen rather than preserve the parent behind an overlay. The paired editor also uses a teal fill rather than the main screen’s Norton-style blue.
  • A title saying Install gives no confidence about whether you are updating this profile, creating a new one, or changing only credentials.
Proposed · not implemented
The same journey should be
  1. Open a target using any entry point.
  2. The same section editor appears; only its initial selected section changes.
  3. Cancel returns to the exact parent you came from.

How this should behave

  • Use the same L3/L4 workspace for setup, parameter edits, and authentication. Entry shortcuts choose the relevant section; they do not create a different interaction model. Keep the blue palette consistent; focus is conveyed through highlights and borders.
  • Titles identify capability + environment / target and say Configure for an existing target. New setup is labelled New setup.
  • Keep the invoking parent visible. Back returns to that parent with its selection preserved, including when the parent is Environments.

04 · Type where the field is

Enter should turn the highlighted field into the editor. A second, distant editor breaks the connection between the value and the action.

Current · observed in the release
Walkthrough
  1. In Authentication, focus Token.
  2. Press Enter.
  3. Type, move the cursor, or paste; inspect where the text appears.

What actually happens

  • Enter opens a separate Edit strip at the bottom of the dialog. The original field remains above, so your eyes and input are separated.
  • A bracketed paste event sent to the Token editor produced no text. This verifies that paste path only; it is not a test of every terminal or clipboard shortcut.
  • Literal typing and Left-arrow cursor editing did work: a test value became abZc. The cursor itself is not generally broken.
Proposed · not implemented
The same journey should be
  1. Highlight Token → Enter: cursor appears in Token.
  2. Paste or type; see the value at that location.
  3. Enter finishes the edit; Ctrl-S saves the form.

How this should behave

  • Enter edits the existing value in place, with a visible cursor and edit focus. Ordinary typing and terminal paste feed that field.
  • While editing, Left / Right move the cursor. Enter finishes field editing; Escape restores that field’s value from before the edit. Neither key accidentally opens another menu.
  • Ctrl-S finishes any active edit, validates, saves once, and applies immediately. Browse is an explicit adjacent control, not a surprise result of Enter on a path value.

05 · Authentication must explain the choice

Token and source kubeconfig are alternatives. The UI should make their state obvious before the user types.

Current · observed in the release
Walkthrough
  1. Choose Authentication in the section list.
  2. Move into the right panel and select Token or Source kubeconfig.
  3. Compare the input instructions and the picker behaviour.

What actually happens

  • Both alternatives look like ordinary empty rows. Mutual exclusion is described in an edit help line, rather than shown as a clear mode in the section.
  • The source kubeconfig explanation does correctly say that AACT imports it and uses managed credential material at runtime. Keep that distinction.
  • Opening the file chooser transfers you out of the editor’s navigation model entirely.
Proposed · not implemented
The same journey should be
  1. Authentication → Right → Enter on Token: edit Token here.
  2. Select Source kubeconfig and type or Browse: it becomes active and Token becomes inactive.
  3. Save: report the actual authentication outcome, not just that a path or token was stored.

How this should behave

  • Keep both alternatives visible. The active alternative is visually identified; the inactive one is dimmed but can be selected and edited to switch authentication mode, as the user requested.
  • Use the exact label Source kubeconfig. Show a separate read-only “Imported credentials: present / missing” observation; do not confuse a saved source path with current authentication health.
  • Environment defaults remain editable. Target-fixed inputs remain hidden from the edit form; Information explains their origin. No credential masking.

06 · Failure is a screen, not a footnote

An unsuccessful operation needs a visible explanation and a route back to fix it.

Current · observed in the release
Walkthrough
  1. Save the raw authentication input form.
  2. Read its narrow Operation result dialog, then return to the parent.
  3. Compare the footer-only logs failure, Cancel, and Check connection results.

What actually happens

  • Authentication failure does open an Operation result dialog. It clips the instruction to run authentication again, fills the remaining space with serialized JSON, and offers only Back. A just-submitted authentication form gives no field-specific reason or direct route to correct it.
  • Other failures, including the observed View logs failure, only appear in the bottom status / border area. Error presentation therefore depends on which action failed. Cancelling a child-input flow is also labelled “Failed: selection cancelled” with null changes/errors JSON.
  • The isolated Check connection result clips a two-line error even in a 170-column terminal. Both result examples show the surrounding black-background inconsistency.
Proposed · not implemented
The same journey should be
  1. Save → foreground progress identifies each step.
  2. Failure → read the full error and achieved state here.
  3. Return to configuration preserves values; change the input or fix the external problem, then save again.

How this should behave

  • Use a foreground blue result overlay with operation, target, failed step, exact error output, and a visible scroll indicator. Wrap long errors; optional raw output can be inspected separately.
  • Keep the submitted values and distinguish Saved from Applied. List each actual successful or failed effect. A failed MCP registration leaves that agent unregistered. No automatic revert.
  • Provide Return to configuration, Retry, and Close. A normal Cancel returns quietly. If an error was caused by external setup, name the exact file / command / endpoint so it can be fixed outside AACT.

07 · Validation belongs beside the input

Input errors and empty choice sets should be understandable before an operation is attempted.

Current · observed in the release
Walkthrough
  1. Edit Local port to 1 and finish the edit.
  2. Open Databases.
  3. Press Enter on its empty selector.

What actually happens

  • The port constraint is reported far from the field while the detached editor remains open. The original valid value is still visible above.
  • Databases looks like an input, but Enter only reports “No choices available in the selected target” in the footer.
  • A selectable control with no choices provides no indication whether databases are optional, missing configuration, loading, or broken.
Proposed · not implemented
The same journey should be
  1. Enter 1: validation appears immediately beside Local port.
  2. Correct that value without leaving the editor.
  3. Databases with no choices explains what is missing and shows the relevant configuration file.

How this should behave

  • Show the entered value and the validation message together: “Port must be at least 1024.” Preserve the edit so it can be corrected. Save focuses the first invalid field.
  • If a target supplies no database choices, show a read-only explanation rather than an empty selectable row. State that database access is optional and identify the target TOML that supplies it.
  • When choices exist, the left-hand database selection determines only its right-hand details, following the same layer philosophy.

08 · Where it is going must be unambiguous

The selectable destination and the actual configuration path must agree.

Current · observed in the release
Walkthrough
  1. Open Destinations for Cluster Inspector.
  2. Inspect the named agents, generic entry, and OpenCode path.
  3. Compare OpenCode in Agents, then inspect a skill-only capability.

What actually happens

  • Cluster Inspector offers generic despite requiring an agent-specific MCP registration. Its destination is blank. That conflicts with the user’s skill-only All policy.
  • This setup screen targets /home/user/.local/share/aact/wsl-opencode-home/.config/opencode/opencode.json; the Agents screen reports /home/user/.config/opencode/opencode.json. The UI never explains the difference. These are visibly different paths; this audit did not attempt a live write to prove which one would receive a registration.
  • Find Session correctly offers All, selected by default, and no MCP rows in L2. However All, Codex and generic can name the same skill directory; Copilot destinations also overlap.
Proposed · not implemented
The same journey should be
  1. Agents section → highlight OpenCode: see detection and the exact destination.
  2. Space chooses the agent; Save attempts those explicitly listed effects.
  3. Show installed only for effects actually completed.

How this should behave

  • MCP capabilities offer named agent destinations only. Show detection, exact chosen config file, and the planned skill / MCP effects for the highlighted agent. Explain any explicit home override.
  • Use one path account across Agents and installation. If multiple config candidates exist, show which one is effective and which one AACT will change. Never present two unexplained answers.
  • Skill-only All means the global ~/.agents/skills directory, selected by default. Explain shared directories instead of implying that identical paths represent separate installations. Form checkboxes are desired choices; result/status checkboxes represent achieved state only.

09 · A file picker is still part of the TUI

The fallback chooser currently stops behaving like the rest of the interface.

Current · observed in the release
Walkthrough
  1. In Authentication, open Source kubeconfig selection.
  2. Try Escape and arrow keys.
  3. Enter the literal word cancel to leave.

What actually happens

  • The release prints a numbered shell-style list and “Path or row number; cd …, up …, cancel”. It is not a navigable picker panel.
  • Escape and arrow escape sequences are inserted into that prompt as text. They can produce a path-not-found error instead of navigation.
  • The frozen configuration stays above the line prompt, leaving two incompatible focus models on screen. Dot directories are listed, but selection is not natural.
Proposed · not implemented
The same journey should be
  1. Browse → file picker appears in the foreground.
  2. Arrows choose a row; Enter opens a directory or selects a file.
  3. Escape returns to Source kubeconfig without changing it.

How this should behave

  • A terminal fallback should be a real modal picker with current path, highlighted rows, explicit Open directory / Select file controls, and the same keyboard focus model.
  • Show dotfiles by default. In file mode, Enter on a directory opens it; Enter on a file chooses it. In directory mode, an explicit Select this directory button removes ambiguity.
  • Escape closes the picker and returns to the same field. A visible editable path field accepts paste. Native OS pickers may be used where available, but this WSL audit only observed the terminal fallback.

10 · Directory collections: preserve what works

Add, edit and remove now exist. Their interaction should become ordinary field editing rather than another hidden mode.

Current · observed in the release
Walkthrough
  1. Open Local Git Repository Map → Inputs.
  2. Use m to add a path manually, then edit the existing path.
  3. Press Backspace on that existing directory.

What actually happens

  • The current release successfully adds, edits and removes a directory in the unsaved form. Backspace works. These are not missing features in this audit.
  • Manual editing is exposed through m in footer help and uses the detached bottom strip. The path row itself does not look like an input.
  • The adjacent Git hosts collection has different wording (“item” versus “directory”), although the same basic collection actions apply.
Proposed · not implemented
The same journey should be
  1. Inputs → directory row → Enter: edit its existing path.
  2. Backspace outside text editing removes that row.
  3. Add directory chooses one folder; repeat to add more.

How this should behave

  • Give each directory row visible Edit and Remove actions, with Enter editing that row in place and Backspace removing it when the list row is focused. In a text edit, Backspace deletes a character.
  • Add opens a one-directory picker. Manual typing is a visible alternative. Keep the collection’s add / edit / remove responsibility in the form.
  • Section arrows select sections only; field arrows select rows within that section only. Show that changes are drafts until Save.

11 · Attach an agent without owning the server

An externally started server can still be usable locally. Unknown ownership needs explanation rather than a dead end.

Current · observed in the release
Walkthrough
  1. In isolated state, open the external endpoint’s profile menu.
  2. Choose Configure agent registrations.
  3. Select Endpoint, then an agent; inspect both right-hand views.

What actually happens

  • The registration dialog already implements the separate Endpoint row and the L3/L4 relationship. Selecting an agent changes its detail pane. This matches an important part of the agreed design.
  • The menu disables Start / Stop because ownership is unknown while leaving Configure registrations available. That distinction is sensible, but it needs a clear server-state explanation.
  • generic is still offered. Remove local registrations unnecessarily includes an Endpoint / Check connection page and calls its button Apply changes, hiding the actual removal effect.
Proposed · not implemented
The same journey should be
  1. External target → Agents: choose local agent registrations.
  2. Endpoint row → Check connection: see the current observation and time.
  3. Save registers selected local agents; Start / Stop remain unavailable when the runtime is not owned here.

How this should behave

  • Overview separately states reachability, ownership, and local registrations. “Ownership unknown” explains why AACT cannot control the process; it does not mean registration is impossible.
  • Keep Endpoint as a dedicated left entry with URI + Check connection on the right. Each agent’s detail shows its exact config path, desired registration, and achieved registration. Named agents only.
  • Remove uses a small centred dialog listing the actual registrations selected for removal, with “Remove selected registrations” and Cancel. It does not change or stop the external server. Use Save for the ordinary configuration form.

12 · Runtime and logs need actionable empty states

A missing container is a normal lifecycle state. The UI currently treats it like a failed command.

Current · observed in the release
Walkthrough
  1. Select the older source’s Cluster Inspector profile.
  2. Open View logs, which is available.
  3. Observe Docker’s no-such-object result.

What actually happens

  • View logs is offered even though no corresponding container exists. It returns to Home and writes Docker’s error through the status / border area.
  • Start on the legacy profile can open the old raw editor with “Connections: 0 items”, while newer configuration uses the Databases section.
  • The observed live profile never started during this audit. A running log stream, Follow / Pause, and a successful Start / Stop lifecycle were not exercised.
Proposed · not implemented
The same journey should be
  1. Target → Logs: get logs or an explained empty state.
  2. If not started, go to its configuration / overview without losing target context.
  3. If running, pause / follow / scroll only that log panel.

How this should behave

  • Logs with no instance explains “No MCP container has been created for this target” and offers the relevant Configure / Start route. Do not ask Docker for nonexistent logs and present that as the user’s mistake.
  • Running logs stay in the target workspace, with Follow / Paused visible and explicit scroll controls. Closing logs never stops the server.
  • A Start action that needs missing configuration directs you to that same configuration workspace and relevant section. It must not resurrect a different legacy editor.

13 · Presets and saved installations are different

The environment browser mixes choices for future configuration with records of past configurations.

Current · observed in the release
Walkthrough
  1. Main menu → Environments.
  2. Compare No environment file, TOML files and Saved profiles.
  3. Select a target → View selected target.

What actually happens

  • The same environment appears in separate TOML and Saved profiles rows, including a different old source. There is no clear account of preset versus installed profile.
  • The TOML viewer does show exact file contents. That is useful. However it does not explain the resolved path for relative certificate values.
  • On the old-source capability, Configure / install is available but only reports “Package is absent from the local catalog; use profile Actions for registrations.” Start can still enter an old editor.
Proposed · not implemented
The same journey should be
  1. Environments → sample-env preset: see its available targets.
  2. Target → Enter: same editor, values prefilled from that preset.
  3. Information: inspect original value, resolved path, and supplying file.

How this should behave

  • Environment presets are source configuration, not proof of installation. Label them as presets. Saved target status belongs to the capability’s target list with its source identified.
  • From Environments, the right pane shows targets in that preset and their capability. Opening a target uses the same configuration workspace and returns to Environments afterward.
  • Old or unavailable source records show an explicit “Package unavailable” state with Locate source / View saved information / Remove local registration as applicable proposals. Do not imply that configuration works. Show both exact TOML and resolved input/path information.

14 · Agents: say what was detected and where writes go

This screen should answer whether an agent is available and exactly which config AACT uses.

Current · observed in the release
Walkthrough
  1. Main menu → Agents → OpenCode.
  2. Inspect config candidates and their priority.
  3. Open View config files → JSONC, then Configure config location.

What actually happens

  • “Detected agents” includes not-detected and unsupported entries. The heading overstates what the list proves.
  • OpenCode’s summary names JSON while the listed JSONC has higher priority. The configuration workspace reports a third path through an isolated home. There is no single explained answer.
  • Exact config viewing works and shows the real file. Configure config location remains a disabled service-pending action, and attempting it only produces footer feedback.
Proposed · not implemented
The same journey should be
  1. Agents → OpenCode: read detection and path resolution in L2.
  2. Enter View exact config: inspect the chosen file.
  3. Back returns to the same agent; registration screens use this same path account.

How this should behave

  • Name the screen Agents. Each row shows Detected / Not detected / Unsupported here, with evidence in L2. Keep unsupported entries read-only rather than implying configuration can work.
  • L2 answers: executable / app found, active home or override, all config candidates, effective file, intended write file, and observed registrations. Explain mismatches explicitly.
  • View exact file remains unmasked and read-only. Configure location is an actual control only if supported; otherwise show a plain limitation explanation. Missing config is not equivalent to a missing agent.

15 · Settings and Help must use the same language

Management screens should follow the panel hierarchy too, with keys that mean the same thing.

Current · observed in the release
Walkthrough
  1. Main menu → Settings.
  2. Enter Environment root; compare its editor with Default agents.
  3. Open Docker actions, then Help.

What actually happens

  • Settings is a single mixed list of editable preferences, diagnostics, disabled service placeholders and Save / Cancel. It does not use the home screen’s hierarchy.
  • Environment root opens an editor titled Edit package inputs. The Actions menu remains Edit root / Default agents regardless of the highlighted settings row.
  • Help describes Enter / F2 as selected row Actions, whereas Home says Open / Focus. This audit’s captured Help does not contain a batch-selection instruction.
Proposed · not implemented
The same journey should be
  1. Settings category → Right: its actual controls.
  2. Enter on an editable value edits that value or opens the specifically named editor.
  3. Help displays the same key meanings as the current screen.

How this should behave

  • Settings uses L1 categories and L2 controls / explanations: Environment source, Agent defaults, Runtime backend, Diagnostics. The action is attached to the highlighted control.
  • Use task-specific editor titles. Show service-unavailable information as explanatory text with an actionable alternative when one exists, not a collection of enticing disabled buttons.
  • Help is a read-only guide to the actual focus states, including editing, picker, buttons, scroll and back. It describes ordinary-key routes for function-key actions.

16 · One keyboard grammar, visible scroll and return

The layer design is only usable if focus, scrolling and Back behave predictably everywhere.

Current · observed in the release
Walkthrough
  1. Resize the isolated release to 100 columns × 23 rows.
  2. Move between list panes and inspect clipped rows.
  3. Edit a draft in a paired form and leave with Escape.

What actually happens

  • Rows below the viewport have no visible scroll track or More-below marker. The position count alone does not explain which pane can scroll.
  • The form has keyboard-reachable Save and Cancel through its Actions area. This works, but the current focus labels and disconnected editor make the route difficult to discover.
  • In an isolated directory-form exercise, Escape from L4 then Escape from L3 returned to Home and discarded the changed draft, without a visible discarded-changes explanation.
Proposed · not implemented
The same journey should be
  1. L1 Enter → L2. L2 Enter → L3 detail workspace.
  2. L3 Right → L4. Up / Down operate only in the focused pane.
  3. Tab reaches Save / Cancel; Ctrl-S saves from the form. Escape backs out one visible level.

How this should behave

  • Show a strong focused-pane title and selected-row highlight. Decorative headings and facts have a different style from actionable rows. Arrows move only within the focused pane; selecting L3 changes L4 content, while moving in L4 never changes L3.
  • Left / Right and Tab move through panes; Tab also reaches the visible button bar. Text editing temporarily owns Left / Right and Backspace. Escape exits the current edit, picker or detail layer, returning one level at a time.
  • Retain a draft while navigating sections. Explicit Cancel abandons it; ordinary Back should not silently discard an edited configuration. This last distinction is a proposal for approval. At narrow sizes keep the layer relationship and a visible More-below / scrollbar indicator; never hide the action bar.

17 · The section names must follow the user’s task

The same layout is reused for other MCPs, but the input grouping still fails to describe what the user is configuring.

Current · observed in the release
Walkthrough
  1. Open Grafana Inspector configuration.
  2. Compare Authentication with Inputs.
  3. Open Azure Inspector and Forgejo, inspecting their complete short forms.

What actually happens

  • Grafana’s Authentication section shows Auth mode = session_cookie, Token and Oauth refresh. Grafana session, Session expiry and Refresh cookie name instead live under Inputs alongside port, host, URL, datasource and certificate.
  • The credentials needed by the selected session-cookie mode are therefore in a different section, while unrelated alternatives remain prominent. A user choosing Authentication cannot finish that task there.
  • Azure places tenant and subscription identifiers alongside local port and host in Inputs. Forgejo puts its target URL in Inputs and token in Authentication. The layout is consistent; the generic section label and field classification are not.
Proposed · not implemented
The same journey should be
  1. Grafana → Authentication: choose the mode.
  2. All required credentials for that mode appear here.
  3. Connection contains URL/listen settings; datasource and TLS settings have clearly named sections.

How this should behave

  • Sections should represent the configuring task: Connection for server/listen addresses, Authentication for all credentials of the chosen mode, and capability-specific settings for datasource, tenant or subscription.
  • Grafana’s Authentication section should contain its mode choice and that mode’s credential controls. Session cookie, expiry and refresh-cookie settings belong together. Token or OAuth controls appear for their corresponding mode. This grouping is a UX proposal, not a change to authentication semantics.
  • Keep package-default and saved-value origin information available without repeating two lines of metadata after every simple field. A concise origin indicator plus Information preserves provenance while improving scanning.

Evidence, method and limits

  • Walked the official installed Linux/amd64 v0.1.4 binary on test-wsl inside existing tmux session 0, window 1. Application pane %2 was controlled from the existing shell pane %3. No new tmux session was created. Source checkout: /home/user/sources/sample-skills.
  • Captured terminal cell contents using tmux capture-pane, with and without ANSI colours. PNGs reconstruct those cells using a monospace font. They preserve the captured text, layout and colours; they are not native OS framebuffer screenshots, and the font may differ from the user’s terminal.
  • Most observations use live settings and state. Conditional external-registration and connection screens use the same released binary with a temporary isolated state directory and temporary agent-home override. The dummy endpoint is http://127.0.0.1:1/mcp, intentionally unreachable. Those captures are labelled as isolated fixtures and prove interaction only, not a healthy installed MCP.
  • The first editing exercise did invoke Ctrl-S in the live raw editor with a temporary dummy Token. It attempted authentication and failed. The dummy value was removed afterward; a final scan of live manager and saved-answer JSON found none of the audit test strings. Later conditional registration screens were isolated. Directory edits were drafts and cancelled. This was not a completely zero-write live walkthrough.
  • The final docker ps output contained no running containers. No successful MCP startup, completed migration, live agent registration, or authentication recovery is claimed. The real AACT was relaunched in the same pane after the isolated exercise.
  • Native macOS/Windows picker behaviour and OS-specific Cmd-V/Ctrl-V delivery were not exercised here. The reproducible paste observation is that an injected bracketed paste event failed to populate the current raw Token editor. Literal typing and cursor insertion did work.
  • Read the prior TUI design specification and the user’s later corrections. Later instructions replace old batch semantics, prescribe L1/L2 and inset L3/L4, require one Save-and-apply action, forbid auto-revert, and reserve All/global skills for skill-only capabilities.
  • All proposed screens and control labels are UX proposals, not approval to implement them. Application code was not changed. No implementation plan, commit, pull request or merge was created for this audit.

How to read the images

Current = captured release behaviour. Isolated fixture = captured release with temporary test state. Proposed = a new static screen illustration. Some proposal data is illustrative, including validation/results and proposed path resolution. It is not a claim about current installation state.
